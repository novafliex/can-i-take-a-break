> 本项目对「自动化证据」与「必须真实设备 / 真实账号的验收」做了严格区分。本文只声称有证据的部分；未完成的验收项如实列出（核对日期 2026-10-25）。

## 1. 测试全景

| 层 | 工具 | 规模 | 运行方式 |

## 2. Go 后端测试

### 2.1 结构

- **Store 层单元测试**：直接驱动领域逻辑（投票、结算、配额、评论状态机）；
- **HTTP 端到端测试**：`httptest.NewServer(api.handler())` 起真实服务，从登录一路走到投票、评论、复核、结算——覆盖真实的路由、鉴权与响应格式；
- **云端集成测试**：连接真实 MySQL（测试自建 / 自删临时库），验证迁移、事务、并发与备份恢复。微信接口全部用 `httptest` 假服务器或重定向 transport 模拟，**测试不需要真实外网与真实微信凭据**。

### 2.2 代表性用例（按主题）

**投票与结算一致性**
- 固定到期结算 + 后续票不可改变已锁定结果；
- 票数不足 / 平票 → 「未形成有效结果」；
- 结算写盘失败 → 内存快照回滚 + HTTP 503 → 重试恰好一次补上（reliability_test）；
- 凌晨 4:00 业务日边界 + 60 goroutine 并发投票无超发（main_test）。

**配额与防刷**
- 24 个并发创建申请只有 5 份成功（同时进行上限）；结案后配额释放（active_quota_test）；
- 每日 20 票 / 20 份申请 / 10 条评论限额与文案。

**内容安全（fail-closed 全链路）**
- 官方登录 → 评论 / 自定义标题全量过审核；三种判定（pass / risky / block）与未知判定的行为；
- token 过期（42001）自动刷新重试；审核服务缺失时游客不能评论、发布返回 503；
- V0.5 旧数据中已发布评论加载时回退为 pending 复核。

**HTTP 契约**
- 游客登录 → 建申请 → 自投被拒（400）→ 投票 → risky 评论 202 → 管理复核 → 结算 → 后续表态的完整端到端流（http_test）；
- 非本人不能补后续（400）、草稿文章对读者 404、审计字段不泄漏（v2_http_test）。

**分页与排序**
- keyset 游标不重不漏 + 动态插入漂移 + 坏游标 400（loop_cloud_test）；
- 文章排序本地与云端契约一致（精选优先、草稿仅管理可见）。

**身份与审计**
- 具名管理密钥解析、操作者由服务端推导、错误分类不泄漏 secret URL（notify_test / wechat_client_test）。

### 2.3 云端集成测试（真 MySQL）

需要环境变量 `CANI_TEST_MYSQL_ADDRESS`（必须指向 `127.0.0.1:`，测试库由代码创建并在结束后删除；未设置则相关用例 Skip，普通 `go test` 不受影响）。覆盖：

- **多实例并发**：12 并发建申请只 5 成功、40 并发投票只 21 成功（封盘上限）、跨实例重启读数一致、结算不重复、事务回滚不落库；
- **迁移与备份**：V6→V7 迁移、备份校验和、结构不匹配回滚、空库保护、恢复后举报记录存活；
- **云端读者端点**：文章上下架对读者端点的即时生效。

## 3. 前端回归测试（102 项）

`tests/frontend.test.cjs` 用 Node.js 内置 `node:test` + `vm.runInNewContext` 加载**真实的页面 JS**，注入 `wx` API 桩与 mock 的 api / notify 模块，直接驱动 `Page()` 注册的对象并断言 data 变化与路由调用。零第三方测试框架。

覆盖四类问题：

1. **基础设施**：8 个页面四件套齐全；401 自动换令牌重放；云托管冷启动的 GET 退避重试（**写请求绝不重放**）；admin 密钥只走管理路径且离页清空。
2. **竞态**：过期响应丢弃（feed / review / 评论排序 / 文章栏目）；切换申请清旧状态；mutation 响应在切换后丢弃；点赞按评论 ID 回写。
3. **业务语义**：平票绝不显示「50% 赞同」；投票中不显示赞成比例；订阅授权必须在点击手势上下文且拒绝不落额度；文章 → 申请的意图传递与降级。
4. **管理端**：分页参数拼接、复核保留分页、申诉 / 删除联动。

## 4. 静态检查（check-miniapp.cjs）

- `app.json` 注册的每个页面 js / json / wxml / wxss 四件套齐全；
- 页面 JS / JSON 可编译（`vm.Script`）；
- **WXML 中所有 bind / catch 事件处理器在 Page 对象上真实存在**（抓「模板引用了不存在的方法」这类运行时才暴露的问题）；
- `project.config.json` 的打包排除清单必须包含 server / tests / scripts / `.env*` / `.git`——**防止密钥与后端代码被打进小程序包**；
- 可选 `--compiler-dir` 参数调用微信开发者工具的 wcc / wcsc 对全部 WXML / WXSS 实际编译。

## 5. 部署链工程化（脚本即测试）

部署脚本在「打包」这一步内置了多重防错，源自真实事故教训：

1. **白名单打包**：仅复制 Dockerfile 与非测试 Go 文件到隔离目录，目录内出现白名单外文件即失败（防上次残留泄漏）；
2. **硬拒绝**：`.env*` 与含 `/data/` 的文件绝不允许进入镜像；
3. **部署守卫断言**：打包前静态断言 articles 路由已在 main.go 分发、建表语句在 cloud_repository.go 中存在——防止「代码在包里、路由没注册」导致线上 404 的事故重演；
4. **密钥文件校验**：部署前校验密钥非占位值、非证书私钥类型、长度 ≥32；**CLI 输出流实时把 4 个密钥值替换为 `[REDACTED]`**；
5. 生成 SHA-256 打包清单供事后核对。
