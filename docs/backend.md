# Go 后端工程 · backend.md

> 本文提炼后端的工程结构与值得展示的技术实现。每一项都对应开发仓库 `server/` 下的真实代码与测试（核对日期 2026-10-25）。

## 1. 工程概览

```
server/
├── main.go               # 类型、Store 领域逻辑、路由分发、鉴权
├── community.go          # 评论 / 点赞 / 举报 / 复核
├── articles.go           # 文章系统与审计
├── requests.go           # 隐私请求 / 申诉
├── notify.go             # 订阅消息
├── wechat_client.go      # 微信 API 客户端（证书懒加载）
├── wechat_moderation.go  # 内容安全 + 登录 + openid 加密
├── cloud_store.go        # MySQL 连接池与请求级门面
├── cloud_repository.go   # schema 迁移、作用域加载、差量落库
├── cloud_delegates.go    # 业务方法的事务委托
├── cloud_backup.go       # 备份 / 恢复 CLI
├── seed*.go              # 演示内容与冷启动选题
├── admin.go + admin.html # 内嵌管理页（仅回环可访问）
└── *_test.go             # 22 个测试文件，约 4000 行
```

- **依赖**：`go.mod` 里只有一个直接依赖 `go-sql-driver/mysql`。没有 Web 框架、没有 ORM、没有 Redis / 消息队列。（产品规划稿中技术方向曾写为 Gin，实现时按接口规模评估后改用标准库——规划与实现的差异以代码为准。）
- **路由**：Go 1.22+ 增强版 `http.ServeMux`。`/api/v1/` 通配后手工分发（便于统一鉴权与结算前置），运维端点（`/health`、`/health/ready`、仅回环的 `/admin`）单独注册。
- **统一响应**：所有响应 `application/json; charset=utf-8` + `Cache-Control: no-store`；错误统一为 `{"error": "中文原因"}`，语义由 HTTP 状态码承担（400 参数 / 401 未登录 / 403 权限 / 422 审核存疑 / 502 微信网络 / 503 存储或审核不可用），数据库错误统一包装对外隐藏细节。
- **请求体防护**：默认上限 4KB 且 `DisallowUnknownFields`；头像 data URL 512KB、文章 64KB 单独放宽。

## 2. 认证与身份

**登录链路**：小程序 `wx.login` 取 code → `POST /api/v1/auth/login` → 服务端调微信 `jscode2session` → 签发令牌。

**隐私优先的身份设计**（这是本项目最值得展示的决策之一）：

- **openid 不落明文**：用户 ID = `"wx_" + hex(HMAC-SHA256(secret, openid))`，数据库中无法还原 openid；
- openid 本体（仅发送订阅消息时必需）以 **AES-256-GCM** 加密存储，密钥来自认证密钥独立派生；
- **令牌**：自研 HMAC-SHA256 签名的无状态 token，payload 为用户 ID + 过期时间（7 天），校验用 `hmac.Equal` 常量时间比较。刻意不用 JWT 库——需要的只是「7 天有效的不透明令牌」，20 行实现换来零依赖与零解析攻击面（无 JWK / refresh 等未用到的能力，属于如实取舍而非能力缺陷）；
- **游客模式**：仅本地开发可用，云端形态强制禁用；
- **管理员**：不走用户令牌，独立使用 `X-Admin-Key` 头。支持「具名密钥表」（密钥名即操作者身份），操作者由服务端从密钥推导后写入审计记录——**不信任客户端自报**；密钥比较同样为常量时间。

## 3. 申请与投票：防重与一致性

这是产品的核心写入路径，也是并发风险最高的地方。三层防线：

**第一层：存储约束。** `bureau_votes` 表主键为 `(application_id, user_id)`——重复投票在存储层就不可能成功，无论应用层怎么写。

**第二层：事务与写序锁。** 所有用户写操作包在一个 8 秒超时的短事务里（READ COMMITTED），事务内先执行 `SELECT migrated FROM bureau_schema WHERE id=1 FOR UPDATE` 拿到全局写序锁，再加载实体、执行业务规则、差量落库。这样做的取舍很清楚：

- 收益：业务代码可以按「单线程」心智模型编写，不必在每个检查点担心竞态；
- 代价：写吞吐被串行化——对当前个人项目的量级完全够用，也是**有意的选择**而非无知的产物（测试验证了并发下的正确性，见下）。

**第三层：业务规则。** 投票前置检查依次为：互动期未结束（截止 + 7 天）→ 非本人申请 → 未投过 → 未封盘（正式票满 21 票）→ 24 小时内未满 20 票。

**并发正确性有实测背书**（真 MySQL 集成测试）：

- 24 个并发创建申请 → 只有 5 份成功（同时进行上限 5）；
- 40 个并发投票 → 只接受 21 票（封盘上限 21）；
- 多实例重启后读数一致；事务回滚不落库；结算恰好执行一次。

**幂等结算与快照回滚**：到期结算把「出结果 + 发 XP」打包成一次快照变更，落库/写盘失败整体回滚并返回 503，重试恰好一次补上；对已结算申请重复调用结算不产生任何变化（回归测试覆盖）。

**配额体系**（全部服务端强制）：

| 配额 | 值 | 目的 |
| --- | --- | --- |
| 同时进行的申请 | 5 份 / 人 | 防刷屏 |
| 每日提交申请 | 20 份 / 人（滚动 24h 窗口） | 防灌水 |
| 每日投票 | 20 票 / 人 | 防机器人式刷票 |
| 单申请封盘 | 21 票 | 控制单申请生命周期 |
| 有效结算门槛 | ≥3 票且非平票 | 避免「1 票批准」这种无意义结果 |
| 每日评论 | 10 条 / 人 | 防灌水 |

## 4. 内容安全：fail-closed 审核

所有用户自由文本（评论、自定义申请标题与理由、投票理由、后续、昵称）必须先过微信 `msg_sec_check` v2（scene=2，携带真实 openid）：

- **先审后发**：评论初始状态一律 `pending`，自动审核通过才公开；
- **fail-closed**：审核服务未配置或调用失败 → 返回 503 拒绝发布，**绝不放行**；检测结果存疑（risky）→ 422 转人工复核；明确违规（block）→ 400 拒绝；
- **人工优先**：自动通过的评论仍可被管理员复核隐藏；自动流程永不覆盖管理员已做的决定；
- **token 管理**：接口调用凭证缓存、过期前刷新，40001/42001 自动换新 token 重试一次；
- **旧数据兼容**：历史版本已发布的评论在加载时回退为 pending 复核，不因升级漏放内容。

评论区另有独立于审核的社区机制：两级楼中楼、点赞（toggle 天然去重，仅公开评论可赞）、举报（按用户去重、不能举报自己、**3 人举报自动隐藏转人工**）、软删除保留占位（回复链不断裂）、我的举报记录可查（云端落独立表，管理员恢复评论后举报记录不丢）。

## 5. 文章系统与操作审计

「聊两句」是运营内容而非 UGC：草稿（draft）→ 上架（published）→ 下架（offline），可重新上架；栏目 today / human / lab；标题 4–30 字、正文 1–20 段等结构化校验。设计要点：

- **上架即合规确认**：文章不走机器审核，运营者的上架动作本身就是人工合规确认（代码注释明确此语义）；
- **每步操作必留审计**：创建 / 修改 / 上架 / 下架 / 精选都追加审计记录（业务接口不提供修改或删除），操作者必填且由服务端推导；
- **一次性内容包**：环境开关控制启动时把编辑部草稿批量上架，幂等（只动 draft 状态）、走与人工完全相同的审计管线；
- 双视图契约：草稿对读者不可见（404），对管理员可见——本地与云端的行为有一致性测试。

## 6. 存储：双形态与云仓储

**本地 JSON 形态**：内存 Store + `sync.Mutex`，写盘用临时文件 + rename 原子替换；每次写操作前做深拷贝快照，失败整体回滚。

**MySQL 形态**的关键设计：

- **作用域查询**：实体按「账号 / 单个申请 / 一页游标」按需加载，绝不全表读入内存（代码注释明确此约束）；
- **差量落库**：事务内对比操作前快照，只写变化的行；投票计数用 `ON DUPLICATE KEY UPDATE` upsert；
- **schema 迁移**：版本化迁移（V6→V7 演示过真实迁移路径），迁移后安装 MySQL 触发器（`bureau_legacy_fence`）**禁止旧版本二进制写旧快照表**——防止回滚部署后新旧格式互相破坏；
- **keyset 游标分页**：广场列表用 `(排序键, id)` 游标翻页，并发插入下不重不漏，坏游标返回 400；
- **备份 / 恢复 CLI**：`-backup` / `-restore` 标志。备份在 REPEATABLE READ 快照事务中导出全表并计算 SHA-256 校验和；恢复仅允许写入空库（防覆盖）、文件以 `O_EXCL` 独占创建（防并发覆盖）、结构不匹配即回滚。

## 7. 微信集成

| 能力 | 实现 | 细节 |
| --- | --- | --- |
| 登录 | `jscode2session` | openid 派生用户 ID + AES-GCM 加密落库 |
| 内容安全 | `msg_sec_check` v2 | fail-closed，token 缓存与自动重试 |
| 订阅消息 | 两类模板（投票结果 / 请求办结） | **授权额度制**：前端授权后上报额度，发送时消耗最旧一条；无额度或无微信身份则静默跳过；发送异步化（goroutine + recover），43101（用户拒收）视为预期不重试 |
| 云托管信道 | OpenAPI 代理证书 | 容器启动后证书才挂载，客户端懒加载并校验主机名 |

## 8. 可观测性与部署

- **探针**：`/health` 存活、`/health/ready` 就绪（检查 MySQL 可用性），配合云托管弹性伸缩；
- **HTTP Server 超时四件套**（ReadTimeout / WriteTimeout / IdleTimeout / ReadHeaderTimeout）齐全；
- **部署脚本守卫**（详见 [testing.md](testing.md) 的工程化部分）：白名单打包、`.env*` 与数据文件硬性拒绝、输出日志实时脱敏、打包前静态断言「路由已注册 + 建表语句存在」；
- **容器**：两阶段 Dockerfile（`golang:1.25-alpine` 构建 → `alpine:3.22` 运行），静态编译 `-trimpath -ldflags="-s -w"`，非 root 用户运行。

## 9. 各亮点的「问题 → 设计 → 限制」小结

| 亮点 | 解决的问题 | 诚实的限制 |
| --- | --- | --- |
| 主键防重 + 写序锁事务 | 并发重复投票、计数漂移 | 写吞吐串行化，不适合高并发 |
| 幂等结算 + 快照回滚 | 重试导致重复结算 / 发 XP | 结算在请求路径内触发，依赖流量；冷启动靠内容值守兜底 |
| fail-closed 审核 | 审核接口故障时内容漏放 | 无审核重试队列，瞬时故障影响用户发布体验 |
| openid 派生 + 加密 | 数据库泄露不泄露用户身份 | 密钥仍在环境变量中，依赖容器安全 |
| 双存储同构 | 本地开发门槛、测试速度 | 两套存储的行为差异需要契约测试看住（已有） |
| keyset 分页 | 深翻页重复/漏数据 | 其余列表仍是 OFFSET（已知、已记录） |

真实的全量测试证据见 [testing.md](testing.md)。
